# 开发门禁规范 — 测试与独立评审

> 制定日期:2026-09-08。**本规范是铁律,优先级高于任何"效率"考虑。**
> 配合 [WORKFLOW.md](./WORKFLOW.md)(工程流程)使用。
> 适用范围:本项目的一切功能开发、bug 修复、重构——只要产出代码变更(将形成 PR),都必须走完整门禁。

## 0. 总览:七道门,一道都不能少

```
⓪ 需求澄清与产品确认(设计之前,与用户探讨)
① 设计(含验收标准)
② 开发实现
③ 自动化测试(本地:构建/单测/lint)
④ 云实例端到端测试(真实环境)
⑤ 向用户汇报 + 用户手动验收(用户验收无误是进入独立评审的前提)
⑥ 独立 Review AI 评审(第二个 AI,冷视角)→ 用户放行后才允许 Merge(合入 main,见 WORKFLOW.md §7)
```

**核心原则:**
- **Issue 文字 ≠ 完整需求**。Issue 只描述问题/方向;从 Issue 到设计方案之间,必须先与用户沟通确认(⓪),AI 要发挥产品经理作用:想清楚该功能在此业务场景下合不合理、用户期望的处理逻辑是什么、UI/UX 应该怎样,拿理解回来与用户对齐,**确认无误后才能进入设计**。需求模糊时,禁止"按字面意思"直接开工。
- **开发 AI 不得兼职 review**。评审必须派独立的第二个 AI(reviewer 子代理),只给 diff + 需求描述,不给开发过程的会话历史。
- **测试环节不可省略**,且**验收标准在设计阶段就要写好**——先想清楚"怎么算做完",再动手写代码。
- **Merge 权在用户手里**:AI 测试通过 + Review 通过 ≠ 可以合并;必须等用户按手动测试文档验收通过并明确放行后,才执行 `gh pr merge`。

## 0.5. ⓪ 需求澄清与产品确认(2026-09-08 新增,起因见 §6)

进入设计前必须完成,产出沉淀到方案文档开头"需求确认"章节:

1. **场景**:这功能给谁用、在什么情况下用、用来干什么(决定入口形态、一致性范围、交付物);
2. **用户处理逻辑**:该场景下用户希望的操作主线是什么、哪些环节用户要介入(如映射确认)、哪些全自动;
3. **产品判断**:功能放在现有 UI 里合不合理(入口/心智),交付物长什么样(如对照表);
4. 与用户探讨确认(用结构化提问收敛关键分歧),把用户的原话结论记入文档。

## 1. ① 设计阶段:必须先写验收标准

开发任何功能/修任何 bug 前,先在方案(仓库 `docs/issue-<编号>-<主题>.md` 或 Issue 评论)中写明:

1. **需求确认结论**(来自 ⓪,直接引用);
2. **改动点**:改哪些文件/模块,为什么;
3. **验收标准(Definition of Done)**,至少包含:
   - **自动化测试**:哪些单测/构建/lint 必须通过;新增功能要评估是否补单测;
   - **云实例端到端测试**:在云 DCU 实例上验证什么场景、预期看到什么(具体到页面、操作、预期结果);
   - **用户手动验收**:用户需要手动走哪些步骤(后续据此写操作文档,见 §5)。

bug 修复同样要求:先写复现条件 + 修复后预期,再改代码。

## 2. ②③ 开发与自动化测试

- 开发完成后,本地门禁全绿才算完成开发:
  ```bash
  cd frontend && npm run build && npm test && npm run lint   # 前端
  # 后端按仓库既有测试命令执行
  ```
- 测试失败禁止进入下一道门;修完重跑,不允许跳过或"先合再说"。

## 3. ④ 云实例端到端测试

- 本项目 GPU 栈功能一律上云 DCU 实例验证(部署教程见 docs/deploy/);
- 前端:rsync 整个 `frontend/src/`(不要只拷单个文件,源码树会漂移)→ 实例上 rebuild + 重启 tmux `frontend` 窗口;
- 按设计阶段写好的验收标准逐条实测(GUI 用浏览器自动化,API 用 curl/脚本);
- 测试产生的临时账号/测试数据**测完即清理**,敏感案卷数据不落实例。

## 4. ⑤ 用户手动验收(独立评审的前提门)

- 自测(③④)全绿后,AI 向用户汇报,汇报必须包含:

1. **做了什么、改了什么**(一句话能说清);
2. **已通过的验证**:自动化测试结果、云实例实测结果;
3. **用户手动测试操作文档**:放在工作区 `docs/acceptance/手动验收-<主题>.md`(**不入库**),内容包含:
   - 如何访问(SSH 隧道命令、地址、用哪个账号登录);
   - 逐步操作步骤(点哪里、填什么),每步的**预期结果**;
   - 验收通过/失败的判断标准;
4. 明确说:"**等你手动验收通过并放行后,我才进入独立评审,评审通过才 merge**"。

- 用户验收不通过 → 回到 ②修复,重走 ③④⑤;
- 用户验收通过后**才派独立 reviewer**(见 §5),评审通过再由用户确认放行 merge。

## 5. ⑥ 独立 Review AI(铁律,merge 前最后一道门)

- **用户验收通过后**,导出 `git diff <BASE>...<HEAD>`,派**独立 reviewer 子代理**冷审:只给 diff + 需求描述 + 相关契约,**不给开发会话历史**;
- Reviewer 结论处理:
  - `REQUEST CHANGES`:Critical/Important 必须修复(或用事实反驳并说明理由),修复后**重新走 ③④⑤⑥**(改动影响用户体验时需用户复验),再出新 PR 或更新 PR;
  - `APPROVE` / `APPROVE WITH NITS`:Minor/Nit 可缓修,记入 Tech Debt Issue;**向用户汇报评审结论,等用户放行**;
- Review 结果与处理过程要在 PR 描述或评论中留痕。
- 用户放行 → AI 执行 `gh pr merge --squash --delete-branch`(PR base=main)并闭环 Issue。

> 顺序变更记录(2026-09-15,用户明确):旧顺序是「开发→自测→独立 review→用户验收」,用户纠正为「你自己开发完先测一遍,然后再让我来验收,我验收无误后再用独立 AI 来 review」——**用户验收是独立评审的前提,不是评审通过后的走过场**。起因:PR #62 在用户未验收时 AI 就先行跑了独立 review。

## 6. 违规记录(自我警示)

- 2026-09-08 PR #16(Issue #9 前端):开发 AI 自查后直接 merge,违反"独立 review"要求,被用户点名;补做的独立 review 抓出 Important 级 bug(复核预览 pseudonym 被降级为 structured),证明自查不可靠。自本规范起,此类操作禁止。
- 2026-09-08 化名替换整体(Issue #9,#7/#8 同病):用户方向性描述模糊,AI 按 Issue 字面直接开工,跳过产品思考(场景/用户处理逻辑/UI-UX 全空白),做出的功能不是用户要的——映射确认被当成"可选增强"而实际应是主流程、化名按文件独立生成导致同批不一致、对照表不是交付物。整改:新增 ⓪ 需求澄清门(§0.5),并对该功能重新走 ⓪ 起的全流程。
