# 开发门禁规范 — 测试与独立评审

> 制定日期:2026-09-08。**本规范是铁律,优先级高于任何"效率"考虑。**
> 配合 [WORKFLOW.md](./WORKFLOW.md)(工程流程)使用。
> 适用范围:本项目的一切功能开发、bug 修复、重构——只要产出代码变更(将形成 PR),都必须走完整门禁。

## 0. 总览:八道门,一道都不能少

```
⓪ 需求澄清与产品确认(设计之前,与用户探讨;2026-09-30 起并入 Issue 构建——AI 把用户一句话反馈扩写成完整 Issue,澄清收敛后用户确认定稿)
① 设计(含验收标准)
①.5 验收方案独立评审(2026-09-30 新增:第二个 AI 只拿 Issue 冷审验收方案,恒真断言打回;修订后设计与验收方案一起交用户点头,详见 §1.5)
② 开发实现
③ 自动化测试(本地:构建/单测/lint)
④ 云实例端到端测试(真实环境)
⑤ 验收:AI 自验收或用户手动验收(设计阶段定验收方案,分级规则见 §4;人工验收时用户验收无误是进入独立评审的前提)
⑥ 独立 Review AI 评审(第二个 AI,冷视角;调 requesting-code-review skill,意见按 receiving-code-review 处理;效果类 PR 附加维度(2026-10-16):测试用例独立评审,见 §5.1——**该节自 ①.5 独立冷审通过、且用户点头之日起生效**)→ 预授权制放行合并(2026-09-30:人工验收类=无 Critical/Important 且用户二次确认;AI 自验收类=无 Critical/Important 汇报后即合;晋级 main 见 WORKFLOW.md §7)
```

**核心原则:**
- **Issue 文字 ≠ 完整需求**。Issue 只描述问题/方向;AI 构建 Issue 时必须先与用户沟通确认(⓪),AI 要发挥产品经理作用:想清楚该功能在此业务场景下合不合理、用户期望的处理逻辑是什么、UI/UX 应该怎样,拿理解回来与用户对齐,**用户确认 Issue 定稿后才能进入设计**。需求模糊时,禁止"按字面意思"直接开工。
- **设计者不得兼写出题人**。验收方案必须经独立第二个 AI 冷审(①.5,只给 Issue 正文 + 验收方案全文,不给设计方案与 diff)——同一 AI 既设计又定验收,会写出永远通过的验收方案。
- **开发 AI 不得兼职 review**。评审必须派独立的第二个 AI(reviewer 子代理),只给 diff + 需求描述,不给开发过程的会话历史。
- **写测试的人不得兼写漏测清单(2026-10-16;自 ①.5 独立冷审通过、且用户点头之日起生效,见 §5.1)**。凡效果类 PR(适用范围见 §5.1),⑥ 的 reviewer 按**两段式**执行:先只看 Issue 正文独立列出应测边界并**留痕**,再交 diff 对照;符合负样本判据的漏测按 §5:118 的 Important 起处理——写修复的人容易只测自己想到的边界。
- **测试环节不可省略**,且**验收标准在设计阶段就要写好**——先想清楚"怎么算做完",再动手写代码。
- **Merge 放行采用预授权制(2026-09-30)**:用户在 ⑤ 验收通过时即预授权"review 无 Critical/Important 即合并";review 通过可直接 `gh pr merge`,出 Critical/Important 则修完重走 ③④⑤⑥ 后回来找用户。涉及真实案卷/主观判断的人工验收类改动,合并前仍须用户二次确认。

## 0.5. ⓪ 需求澄清与产品确认(2026-09-08 新增;2026-09-30 起在构建 Issue 阶段一并完成,见 WORKFLOW Step 1)

进入设计前必须完成,结论沉淀进 Issue 正文(场景/边界/验收草案)与方案文档开头"需求确认"章节:

1. **场景**:这功能给谁用、在什么情况下用、用来干什么(决定入口形态、一致性范围、交付物);
2. **用户处理逻辑**:该场景下用户希望的操作主线是什么、哪些环节用户要介入(如映射确认)、哪些全自动;
3. **产品判断**:功能放在现有 UI 里合不合理(入口/心智),交付物长什么样(如对照表);
4. 与用户探讨确认(用结构化提问收敛关键分歧),把用户的原话结论记入文档。

## 1. ① 设计阶段:必须先写验收标准

开发任何功能/修任何 bug 前,先在方案(仓库 `docs/issue-<编号>-<主题>.md` 或 Issue 评论)中写明:

1. **需求确认结论**(来自 ⓪,直接引用);
2. **改动点**:改哪些文件/模块,为什么;
3. **验收标准(Definition of Done)**,至少包含:
   - **自动化测试**:哪些单测/构建/lint 必须通过;新增功能要评估是否补单测;
   - **云实例端到端测试**:在云 DCU 实例上验证什么场景、预期看到什么(具体到页面、操作、预期结果);
   - **用户手动验收**:用户需要手动走哪些步骤(后续据此写操作文档,见 §4;仅人工验收时需要);
   - **验收方案(谁来验收)**:AI 自验收或人工验收,判据见 §4,写进设计评论。

bug 修复同样要求:先写复现条件 + 修复后预期,再改代码。

## 1.5. ①.5 验收方案独立评审(2026-09-30 新增)

> 起因:设计 AI 与验收方案出自同一上下文,产出"永远通过"的验收方案——设计者=出题人,验收被写成"验证我打算做的事"而非"验证用户的问题解决了"。修复:派独立冷视角 AI 只拿 Issue 攻击验收方案。

- **时机**:设计+验收方案成稿后、交给用户确认前;**所有 Issue 一律过此门,不分大小**(上游出错下游全白跑)。
- **派发方式**:调 `reviewing-acceptance-plan` skill。子代理输入**只有 Issue 正文 + 验收方案全文**——绝不给设计方案、diff、实现意图或会话历史,否则独立性破功。
- **评审四步**(skill 内置):
  1. **独立预期**:评审员只依据 Issue 先独立起草"问题解决"的预期结果清单,再与方案对比列分歧;
  2. **负样本检验**:逐条回答"bug 不修/功能不做,这条验收会是什么结果"——答不出"会失败"即恒真断言,判无效打回;
  3. **攻击面补充**:异常输入、并发、大文件/极端规模、空值、权限,以及**所有部署链覆盖**(本地 compose / docker nginx / 云 DCU;GPU 栈改动验证环境必须在云实例,门禁④);
  4. **环境可达性**:指出验证环境 AI/用户触达不到的条目。
- **结论处理**:按 `receiving-code-review` 纪律处理(先澄清全部不明项、逐条验证、有据反驳);分歧修订进方案,无法收敛的分歧摆给用户裁决。
- **用户点头**:修订后的**设计与验收方案一起**交用户确认,确认后才进入 ② 开发。方案此后如有实质变更(影响面/验收方式变化),重新过本门。

- **判据必须由实测锚定(规则 A;2026-10-17 新增)**:
  - 任何验收判据的**阈值、方向、比较量**,必须附一次**最小机制的实测证据**(探针命令 + 运行输出/哈希),写清"这个数字从哪来";写不出实测就先写探针,**探针没跑完不许定阈值**。
  - 反例(本项目实测):#123 的 AC1(b) 把"单页耗时"当分母,而 k=3 并发下第一页自己的就绪时间就是 14–16s、单页耗时 6.2s ⇒ **该判据物理上不可能通过**,最终只能用户裁决"接受 FAIL 合入";#96 的 AC2 建立在"切 MinerU 更快"这一**从未实测的前提**上,探针一跑即被证伪。
  - 目的:判据是**先写后验机制**的产物时,必然批量产出"恒真/测不了/不可能通过"的条目。实测锚定把这一步提前到写判据之前。
- **①.5 收敛规则(2026-10-17 新增;用户批准)**:
  - **全量冷审最多 3 轮**;第 4 轮起只允许**窄复核**——评审员只看"上一轮未闭合项"与新的**语义**风险,不做全量重审。
  - **文本一致性问题不再开新轮**:行号、措辞、编号、跨引用这类**机器可判**的漂移,一律交给机械对账(辅仓 `scripts/plans/plan_citation_lint.py` + 规则 B"方案正文不复述代码行号")+ 作者自证脚本输出,评审只需核对"脚本输出 + 未闭合项"。
  - **不受此限制的**:判据**语义**类问题——恒真断言、可失败性、预注册、负样本、变异自证——仍必须逐轮改毕,一条都不许松。
  - 起因(本项目实测):Issue#96 连过 8 轮全量冷审、每轮均 REVISE,而**代码与用例侧在第 6 轮后已达标**;同族"处置表自称已改、正文没改"连抓三轮(r6 13/18、r7 13/18、r8 13 处),根因是**机器可判的东西在人肉维护**。

## 2. ②③ 开发与自动化测试

- 开发完成后,本地门禁全绿才算完成开发:
  ```bash
  cd frontend && npm run build && npm test && npm run lint   # 前端
  # 后端按仓库既有测试命令执行
  ```
- 测试失败禁止进入下一道门;修完重跑,不允许跳过或"先合再说"。

## 3. ④ 云实例端到端测试

- 本项目 GPU 栈功能一律上云 DCU 实例验证(部署教程见 docs/deploy/);
- 前端:rsync 整个 `frontend/src/`(不要只拷单个文件,源码树会漂移)→ 实例上 rebuild + 重启 tmux `frontend` 窗口;
- 按设计阶段写好的验收标准逐条实测(GUI 用浏览器自动化,API 用 curl/脚本);
- 测试产生的临时账号/测试数据**测完即清理**,敏感案卷数据不落实例。

## 4. ⑤ 验收:AI 自验收或用户手动验收(独立评审的前提门)

> **验收人分级(2026-09-29,用户明确)**:设计阶段(①)写验收标准时同步定**验收方案——谁来验收**:
> - **AI 自验收**:改动可由 AI 依客观标准完全核对时(典型:纯 UI 显示/文案/样式、纯接口行为——AI 具备浏览器操作与页面视觉检查能力,能自行访问前端逐条实测;API 用 curl/脚本)。AI 按验收标准逐条实测并留证(截图/命令输出贴进 PR),通过后**直接进入 ⑥ 独立评审**,免产出手动验收操作文档;合并授权见 §5 预授权制(2026-09-30 起:review 无 Critical/Important → 汇报结论与证据后即合并,汇报不阻塞合并)。
> - **人工验收**:涉及真实案卷数据、业务正确性/主观效果判断、或验证环境 AI 触达不了的改动,维持本节原流程(操作文档 + 用户手动验收)。
> - 设计评论未写验收方案 → 按"人工验收"从严处理;
> - 开发中实际改动超出设计时验收方案/影响面(如实际触及真实案卷或主观判断)→ **重新分级,从严处理**(默认转人工)。

- 自测(③④)全绿后,按上方分级走对应流程——**AI 自验收**:按验收标准逐条实测并留证(截图/命令输出),通过后直接进入 ⑥;**人工验收**:AI 向用户汇报,汇报必须包含:

1. **做了什么、改了什么**(一句话能说清);
2. **已通过的验证**:自动化测试结果、云实例实测结果;
3. **手动测试操作文档**(仅人工验收):放在工作区 `docs/acceptance/手动验收-<主题>.md`(**不入库**),内容包含:
   - 如何访问(SSH 隧道命令、地址、用哪个账号登录);
   - 逐步操作步骤(点哪里、填什么),每步的**预期结果**;
   - 验收通过/失败的判断标准;
4. **流程区分**:人工验收明确说:"**等你验收通过并放行后,我才进入独立评审,评审通过且无 Critical/Important 即 merge(人工验收类合并前仍向你二次确认)**";AI 自验收的汇报发生在 ⑥ **之后**——评审结论与逐条实测证据一并向用户汇报,汇报不阻塞合并(授权依据见 §5 预授权制)。

- 验收不通过 → 回到 ②修复,重走 ③④⑤;
- 验收通过后(人工验收 = 用户手动验收;AI 自验收 = 逐条实测留证通过)**才派独立 reviewer**(见 §5);review 通过且无 Critical/Important → 人工验收类由用户二次确认后 merge,AI 自验收类汇报结论与证据后即 merge。

## 5. ⑥ 独立 Review AI(铁律,merge 前最后一道门)

- **验收通过后**(人工验收 = 用户手动验收;AI 自验收 = 逐条实测留证通过,见 §4),导出 `git diff <BASE>...<HEAD>`,**调 `requesting-code-review` skill** 派**独立 reviewer 子代理**冷审:只给 diff + Issue 需求描述 + 相关契约,**不给开发会话历史**(**效果类 PR 例外见 §5.1:第一段只给 Issue 正文,先拿独立边界清单留痕,再交 diff 对照**);评审清单含完成性对照验收方案、回归与副作用(其他链路/各部署链/共享模型层影响、是否引入新默认行为或新限制)、规范符合性(分支模型/PR 描述/CHANGELOG/文档同步)**、以及效果类 PR 的 §5.1 两段式留痕——由派发方在 PR 描述记录两段交付的时间戳并声明先后(不由执行 §5.1 的同一 reviewer 自证)**;
- Reviewer 结论处理(按 `receiving-code-review` 纪律:先澄清全部不明项、逐条对照代码库验证、有据反驳):
  - `REQUEST CHANGES`:Critical/Important 必须修复(或用事实反驳并说明理由),修复后**重新走 ③④⑤⑥**(改动影响用户体验时需用户复验),再出新 PR 或更新 PR;
  - `APPROVE` / `APPROVE WITH NITS`:Minor/Nit 可缓修,记入 Tech Debt Issue;按下方放行条目处理(预授权制)。
- Review 结果与处理过程要在 PR 描述或评论中留痕。
- **放行(2026-09-30 预授权制)**:授权依据按验收分级——**人工验收类**:用户在 ⑤ 验收通过时预授权"无 Critical/Important 即合并",review 通过后用户二次确认 → AI 执行 `gh pr merge --squash --delete-branch`(PR base=preview);**AI 自验收类**:review 通过(无 Critical/Important)→ 向用户汇报评审结论与证据后即合并,汇报不阻塞合并;任一类出 Critical/Important → 修完重走 ③④⑤⑥ 后回来找用户。

> 顺序变更记录(2026-09-30,用户明确):review 通过后的二次放行改为预授权制——用户验收即为放行点,简化单人开发往返;用户保留对 Critical/Important 的复核权。

> 顺序变更记录(2026-09-15,用户明确):旧顺序是「开发→自测→独立 review→用户验收」,用户纠正为「你自己开发完先测一遍,然后再让我来验收,我验收无误后再用独立 AI 来 review」——**用户验收是独立评审的前提,不是评审通过后的走过场**。起因:PR #62 在用户未验收时 AI 就先行跑了独立 review。(2026-09-29 起验收人按 §4 分级:AI 自验收类由 AI 留证验收后进评审,人工验收类维持本顺序。)

## 5.1. ⑥ 附加维度:效果类 PR 的测试用例独立评审(2026-10-16 新增,承旧仓 #74;**自 ①.5 独立冷审通过、且用户点头之日起生效**)

> 起因:修复一直追着单份材料的具体问题跑,而测试由写修复的人自己写——**写测试的人容易只测自己想到的边界**。§1.5 冷审的是「验收方案」,测试用例是动工后才出现的产物,正落在本维度射程;做法是把 §1.5 的冷输入三步法移植到 ⑥。
> **生效时点(先读)**:本节在 ①.5 独立冷审通过、且**用户点头**之日生效;在此之前按旧规范执行(此前按草案跑过的记「预演」,见文末),不做追溯适用。

- **适用范围(以改动面为唯一判据,不按 Issue 文案关键词,避免漏与滥)**:
  - **一律适用**:`git diff` 触及下列任一(或同类)文件——锚点示例:`backend/app/services/hybrid_ner_service.py`、`backend/app/services/has_client.py`、`backend/app/services/has_service.py`、`backend/app/services/agent_md_ner.py`、`backend/app/services/vision_service.py`、`backend/app/services/vision_config.py`、`backend/app/services/mineru_parse_client.py`、`backend/app/services/ocr_has_vision_service.py`、`backend/app/services/text_layer_docline_service.py`、`backend/app/services/entity_type_service.py`、`backend/app/core/safe_regex.py`、`backend/app/services/vision/**`、`backend/config/preset_entity_types.json`、`eval/gt/**`、`eval/benchmarks/**`、`eval-ng/**`,以及 `eval/scripts/**` 中**定义评测口径**者(指标定义/评测入口/门限判定类脚本)。**示例非穷尽,判定标准=「是否改变实体识别产出或评测口径」**:文件不在示例内、但改动会改变识别产出或评测口径时同样适用;命名两可时**按「会」推定适用**。**只改落入上述适用范围的测试文件的 PR 同样适用**(测试正是本维度要审的产物;如 `backend/tests/**`、`eval*/**/tests/**` 里与识别产出/评测口径有关者);**纯报告渲染与一次性脚手架脚本不含口径定义者不算**(如 `eval/reports/**` 下的产物)。
  - **不要求**(豁免以「不改识别产出、不影响评测口径」为前提):纯前端 UI/交互、纯文档、CI/构建脚本、纯报告渲染/脚手架脚本(不含口径定义)、与识别产出无关的内部重构。**豁免须举证**:「与识别产出无关的内部重构」须在 PR 描述写明「仅内部重构、无行为差异」并附可核验证据(检定/对拍/前后输出逐字一致);上述纯前端/纯文档/CI 三类只需在 PR 描述注明类别。举证不足的按适用处理。
- **两段式派发(独立性可核验的关键;两段派给**同一个** reviewer 子代理,不另派第三方)**:
  1. **第一段——只看缺陷描述**:派发方**只交付** Issue 正文(缺陷描述/复现条件/受影响面;新增功能类则为功能规格与验收草案),**不给 diff、不给 PR 内测试、不给会话历史**,并声明「本段输入不含 diff」;第一段期间评审员**不得自行获取** PR/diff/git 内容(不得 `gh pr view`/`gh pr diff`/`git show` 等)。评审员先独立产出「应测边界清单」,并以 **PR 评论原文留痕**(公开可查时间戳;派发方评审日志只作辅助,不得单独充当留痕)。**该清单评论一经发布不得编辑**(需更正时另发新评论并注明,原评论保留),否则「先发占位、看完 diff 再补」可伪造先后顺序。**派发方随后在 PR 描述记录两段交付的时间戳并声明先后**;**清单评论时间必须早于第二段输入交付**——顺序反了即本节结论无效、须重做。
  2. **第二段——对照查漏**:把 `git diff <BASE>...<HEAD>`(含 PR 内已有测试)交给同一 reviewer,拿独立清单逐项对照,列出**漏测边界**与**恒真断言**。
  3. **判定与处置**:逐条回答**负样本判据**——「若这条边界被破坏(或把实现对回缺陷状态),**本次缺陷会复发或被掩盖**吗?」——按下表定级(**判据封闭:仅两维、仅四格,不得引入第三档**;每格判断仍须给证据):

     | 该边界是否被缺陷描述/验收标准明确覆盖 | 破坏后会不会复发或掩盖回归 | 定级与处置 |
     |---|---|---|
     | 覆盖 | 会 | **漏测** ⇒ **Important 起**,按 §5:118 走重走链 |
     | **未覆盖** | **会** | **同上(Important 起)**——Issue#54 的动机正是「两头都没人兜」的边界,不因「Issue 没写上」而降级 |
     | 覆盖 | 不会 | 记 **Minor**,按 §5:119 记入 Tech Debt Issue,**不作为打回依据** |
     | 未覆盖 | 不会 | 同上(Minor) |

     - 走重走链口径:修完重走 **③④⑤⑥**;若**仅增改测试、无行为改动**,可只重走 **③⑥** 并在 PR 描述注明理由。
     - **恒真断言**(把实现对回缺陷状态,这条测试仍不失败)与**漏测同级 Important 起**,不得作为通过依据;若该断言另有具名用例承担判别性(PR 里写明「此断言不具判别性,判别由 X 承担」并列出 X),可记 Minor 豁免。
     - 独立清单**不要求穷尽**,但**至少覆盖缺陷描述/验收标准所指的每一类边界**(少于此即判第一段不合格)——否则清单可任意稀薄,本维度会被空过。
